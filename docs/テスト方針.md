# テスト方針

Python・フロントエンドに共通する判断基準と、fixture・モックの使い分けを定めます。
責務の配置と共通化の判断は[設計・実装方針](設計・実装方針.md)に従います。

## ケースの選び方と読みやすさ

- 実装前に守る振る舞い・境界・不変条件と、検出したい回帰を確認する。
- 正常・異常・境界は、異なる判断や失敗を検出する最小入力を選ぶ。同じ経路の値違いや総当たりを増やさない。
- 既存ケースへのassert追加・修正で十分ならケースを増やさない。別レイヤーには受け渡し・変換・連携に固有の失敗だけを追加する。
- Pythonのケース名は `test_` に続けて条件と期待結果を日本語で書く。Vitestの `describe`・`it` の説明も日本語にし、対象識別子は `App`・`fetchGreeting` など元の表記を併記してよい。
- `pytest.mark.parametrize` の自然言語の `id` は日本語にする。似た入力と期待値は、読みやすくなる場合だけパラメーター化する。
- 複雑なテストは `# GIVEN: 前提`・`# WHEN: 操作`・`# THEN: 期待結果` で段階を説明する。TypeScriptでは `//` を使う。単純なテストに自明な説明を強制しない。
- テストデータは原則スター・ウォーズかF1の題材を使い、実在の顧客情報・個人情報は使わない。
- 時刻・乱数・UUIDは必要に応じて固定・注入する。固定時間の `sleep` で完了を待たず、非同期処理や条件の成立を待つAPIを使う。

テストの配置は対象の領域・レイヤーに合わせます。実装を `domains/`・`repositories/` などへ分けた場合はテストも対応させ、未採用のレイヤー構造を先回りして作りません。
Pythonは対象の関数・メソッドごとに `Test...` クラスを作り、正常・異常・境界ケースを同じクラスへまとめます。モデル・スキーマの検証は型ごとにまとめます。サービス全体を巨大な1クラスにせず、ケースごとのクラスにも分けません。関連する対象を同じモジュールへ置いてもクラスは対象ごとに分けます。
クラス名は `TestCreateGreeting` など対象を示し、メソッド名は日本語にします。`__init__`・クラス属性で可変状態を共有せず、準備と解放はfixtureを使います。Vitestの `describe` も対象と振る舞いに沿ってまとめます。

```python
class TestCreateGreeting:
    def test_名前を指定すると挨拶を返す(self) -> None:
        assert create_greeting("ルーク") == "こんにちは、ルークさん！"

    def test_空の名前なら入力エラーにする(self) -> None:
        with pytest.raises(ValueError):
            create_greeting("")
```

この例は `pytest` と `create_greeting` をimport済みのテストモジュールを前提とします。

## fixture・ヘルパーの責務

最初に対象へ適用される `conftest.py` と既存のfixture・ヘルパーを確認します。短い準備は直接書き、長い・非自明な準備や同じ意味を持つ前提だけを抽出します。

| 用途 | 配置・扱い |
| --- | --- |
| 1ケースだけの短い入力・事前条件 | テスト内に明示する |
| 1モジュールだけの共通前提・モック | そのテストモジュール内のfixture／ヘルパー |
| 複数モジュールで共有する同じ意味の前提 | 最も近い `conftest.py` |
| 実接続の設定・認証・クライアント生成・解放 | 対象領域の `conftest.py` に明示要求するfixtureとして置く |
| DBへの繰り返し登録 | データ準備だけを行う保存ヘルパー |

fixtureは一律にルートの `conftest.py` へ集めず、必要なテストが引数・依存fixture・`usefixtures` で明示的に要求します。広範囲の `autouse` にモックや外部クライアント生成を置かないでください。テスト内の `with patch(...)` で寿命が明確なら、fixtureへ移す必要はありません。

- ヘルパーに検証対象の操作やassertを隠さない。保存ヘルパーから検証対象のアプリケーションサービス（`application_service`）を呼ばない。
- データ準備だけのために解析・生成・検索登録など全処理を実行しない。制約・外部キーを満たす状態を直接準備する。ただし連携自体を検証するテストは実際の処理を通す。
- fixtureは原則function scopeとし、可変状態・モック履歴・DBデータをケース間へ漏らさない。module／sessionへ広げる場合は、共有可能な読み取り専用資材とケース固有の状態を分ける。
- `yield` と `finally`、コンテキストマネージャーなどで失敗時も解放する。複数資源は順に確保・解放し、`yield` 到達前の失敗で資源が残らないようにする。
- 設定値の準備と接続先の差し替えを分ける。アプリ起動で通信クライアントを作るなら、起動fixtureからモックfixtureへ依存させ、起動前から終了まで差し替えを有効にする。引数の並び順に依存しない。

例えば次のfixtureは、前提だけを用意し、通信の操作とassertは各ケースに残します。

```python
from collections.abc import Iterator

import pytest
from fastapi.testclient import TestClient

from app_base_backend.main import create_app


@pytest.fixture
def api_client() -> Iterator[TestClient]:
    with TestClient(create_app()) as client:
        yield client
```

共有する前提が不要な数行のテストまで、このfixtureへ置き換える必要はありません。単なる重複削減のための共通化は避けます。

## モックと実物の使い分け

「外部依存だから全部モック」でも「すべて実接続」でもなく、何を保証したいかで選びます。

| 検証する責務・保証 | 使用するもの |
| --- | --- |
| ドメインモデル（`domain`）や純粋な業務計算 | 実物を直接呼ぶ。検証対象をモックしない |
| リポジトリ（`repository`）の保存・取得、DB制約・トランザクション・競合・冪等性 | テスト用DB・ストレージ。公式エミュレーターがあれば優先する |
| 外部通信を担うドメインサービス（`domain_service`）の接続・SDK・応答との対応 | 公式エミュレーター・公式テスト用実装を優先し、なければ管理されたローカル実接続テスト |
| 外部連携を利用するアプリケーションサービス（`application_service`）の判断・処理の調整 | ドメインサービス（`domain_service`）の公開境界をモックする |
| 再現しにくい認証失敗・通信障害・SDK例外・部分失敗 | 理由をコメントし、必要な境界だけモックする |
| Vue画面の状態・表示・操作 | 通信境界を差し替え、Query・コンポーネントなど検証対象は実物を使う |
| フロントエンドのAPIクライアント | fetchなどの通信境界で応答・エラーを制御し、URL・応答変換を検証する |
| 画面とFastAPIの実際のつながり | 開発サーバーやDocker経由の結合確認。モックした画面テストで代用しない |

保存確定・ロールバックなどの保証は実DBで確認し、高速化のためにその境界をモックへ置き換えません。レスポンスだけで確認できる項目を、毎回DBから再取得して重ねて検証する必要もありません。
外部SDKのページング・通信方式を再実装した独自fakeを、正常系の接続検証の代わりに作らないでください。実境界で再現できる正常・異常は実物・エミュレーターで確認し、上位の判断は公開境界のモックで確認します。

### モックの適用・assert

- 実装内部の補助関数ではなく、検証対象外の公開境界を必要最小限差し替える。Pythonのpatchは呼び出し元が名前を参照する場所に適用する。
- 呼び出し回数・引数をassertするのは、二重実行防止・再試行・後続処理の抑止・依存先へ渡す値など、呼び出し方自体が要件の場合だけ。返り値で十分なら内部の呼び順まで固定しない。
- モックの解除・グローバル設定の復元を必ず行い、実接続を確認するケースへ同じモックを混入させない。

### 実接続の安全性

このひな形にはDB・クラウドの実接続テストはまだありません。追加する場合は以下を満たしてください。

- 対象リソース・認証・必要権限・費用・データの後片付け・実行手順を対象READMEに記載する。本番接続や破壊的操作を暗黙に選ばない。
- 外部クラウドなどへの実接続は、明示的なテスト用設定があるローカル実行に限定する。`CI`・`GITHUB_ACTIONS` では認証・クライアント生成・通信より前にスキップする。
- テスト用DB・公式エミュレーターを使うCIテストは、この一律スキップの対象外。必要なサービスをCIで明示的に準備する。
- 非決定的な文言の完全一致ではなく、契約・構造・要求との対応を検証する。認証情報・生の機密データをassertメッセージやログへ出さない。

## Vitestの準備と後片付け

fixture／ヘルパーはPython同様に用途に近い場所へ置き、`beforeEach` に全ケース不要の重い準備を詰め込みません。
`QueryClient` はテストごとに生成し、終了時にコンポーネントをunmountしてキャッシュをclearします。Vitestの `clearMocks` は履歴の消去、`restoreMocks` はspyなどの復元、`unstubGlobals` は `vi.stubGlobal` の解除を担当します。これだけで任意のモジュール状態や副作用がすべてリセットされるとは考えないでください。
非同期表示は `flushPromises`・`vi.waitFor` などで待ちます。jsdomは実ブラウザーではないため、表示・フォーカス・ブラウザー互換性の保証は別途必要です。

## 現在のサンプルと実行

Storybookは表示部品の正常・読み込み・未取得・エラー状態とplay・アクセシビリティを実ブラウザーで確認します。準備・実行は [TypeScript・VueのStorybook](TypeScript・Vue.md#storybook) を参照してください。

- core：実物の挨拶生成と入力不正を直接検証。
- backend：実際のFastAPI・core・一時ディレクトリを使い、HTTP変換とSPA配信を検証。業務ロジックやファイル配信をモックしない。
- frontend：fetch境界を差し替え、APIクライアントとVue画面の表示・再取得を検証。

実行は `mise run test`、個別実行は `mise run //projects/app/backend:test` などです。実接続が必要な検証を未実施・スキップした場合は、通常のテスト成功で代替したと扱わず、未確認の保証と理由を報告します。
