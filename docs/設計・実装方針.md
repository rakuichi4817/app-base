## 基本方針

責務を分けるレイヤードアーキテクチャを参考にします。ただし、すべての機能に全レイヤーのディレクトリ・クラスを作る方式ではありません。必要な責務が生まれた時点で分離し、単に次の関数を呼ぶだけの中継層は増やしません。

以下は一般的な用語と、このひな形を拡張する際の配置方針の対応です。一般論として唯一の正解を示すものではなく、このリポジトリで採用する責務分担です。括弧内はコード上の名前です。

## レイヤーと責務

| 名称 | 担当する責務 | この構成での配置先 |
| --- | --- | --- |
| プレゼンテーション（`presentation`） | HTTPなどのプロトコルとアプリケーションの境界。入出力・エラー応答の変換 | backend。ルーター（`router`）とスキーマ（`schema`）で構成し、必ずしも同名フォルダーは作らない |
| ルーター（`router`） | HTTPパス・ヘッダー・ステータスなどの処理とユースケースの呼び出し | backendの `routers/` |
| スキーマ（`schema`） | APIのリクエスト・レスポンスと入力制約の定義 | backendの `schemas/` |
| アプリケーションサービス（`application_service`） | 複数の処理を組み合わせるユースケースの調整、トランザクション、実行順序の管理 | backendなど各利用側の `application_services/` |
| ドメインモデル（`domain`） | 業務固有の状態・不変条件・振る舞い | coreの `domains/` |
| ドメインサービス（`domain_service`） | 単一のドメインモデルに自然に置けない業務ルール、外部サービスを利用した業務機能 | coreの `domain_services/` |
| リポジトリ（`repository`） | アプリケーションが扱うデータ・ファイルの保存と取得。DB・ストレージへの具体的なアクセス | coreの `repositories/` |
| インフラストラクチャー（`infrastructure`） | 一般的にはDB・ストレージ・外部APIなどの技術的な実装 | この構成では一律に集約せず、後述のとおり責務別に配置 |

配置先は拡張時の例です。現在の最小サンプルには、これらのディレクトリを先回りして作っていません。関数かクラスかの選択と、どのレイヤーが責務を持つかは別に判断します。

## 依存方向と処理の所有者

基本の呼び出しは、プレゼンテーション（`presentation`）→ アプリケーションサービス（`application_service`）→ coreのドメインモデル（`domain`）・ドメインサービス（`domain_service`）・リポジトリ（`repository`）です。

- coreはbackend・FastAPI・HTTPの応答形式へ依存しない。
- アプリケーションサービス（`application_service`）は各利用側に置く。複数アプリから利用されても、ユースケースの調整を機械的にcoreへ移さない。
- HTTPの入力検証・HTTPエラーへの変換はプレゼンテーション（`presentation`）が担当する。検証済み入力を内部へ渡す。
- 業務上の不変条件はドメインモデル（`domain`）が所有する。Pydanticを使うだけでAPIのスキーマ（`schema`）に分類しない。
- クライアントの生成・注入・終了、トランザクションの開始・確定・取り消し、非同期タスクの開始・停止・終了確認はアプリケーション側が管理する。
- リポジトリ（`repository`）がユースケース全体を勝手にコミットしたり、ドメインモデル（`domain`）が通信クライアントの寿命を管理したりしない。

## インフラストラクチャー（`infrastructure`）をどう扱うか

一般的な設計では、リポジトリ（`repository`）のインターフェースを内側に、DBやSDKを使う具体実装をインフラストラクチャー（`infrastructure`）に分けることがあります。
この構成では、その分離や厳密なクリーンアーキテクチャを必須にはしません。外部依存があることだけを理由に、別の層・インターフェース・ラッパーを作らない方針です。

| 処理の例 | この構成での扱い |
| --- | --- |
| DBへの保存・検索、ストレージへのファイル保存・取得 | リポジトリ（`repository`）に具体実装を置く |
| 外部APIを利用した生成・解析などの業務機能 | ドメインサービス（`domain_service`）に置く |
| 複数の処理が使う通信設定・認証・SDK接続 | 必要な場合だけcoreに技術的な共通クライアントを置き、呼び出し元へ注入する。業務判断は置かない |
| API呼び出しの成功を確認してからDBへ保存 | アプリケーションサービス（`application_service`）がドメインサービス（`domain_service`）とリポジトリ（`repository`）を調整する |
| SDKクライアントの生成・破棄、設定値の読み込み、依存の組み立て | backendなどアプリケーション側の起動・終了処理や依存注入で行う |
| Terraform・クラウド資源・配備設定 | 必要になればリポジトリ直下の `infra/` などへ置く。アプリ内部の層とは別物 |

ドメインモデル（`domain`）は原則としてI/Oを行いません。ただし自身の生成・表現変換に閉じたSDK型の参照まで一律に禁止しません。外部通信・再試行・クライアント管理はモデルの外で扱います。
差し替えの必要性や実際の依存境界が生じた場合はインターフェース分離を検討できますが、テストのためだけにすべてを抽象化しないでください。

## 現在のサンプルとの対応

- `backend/src/app_base_backend/main.py`：プレゼンテーション（`presentation`）の最小例。ルーター（`router`）とスキーマ（`schema`）を同じファイルに置く。
- `core/src/app_base_core/greeting.py`：HTTPから独立した、状態を持たない共通ロジックの例。単純な関数で表現できるので、ドメインモデル（`domain`）やドメインサービス（`domain_service`）のクラスを増やさない。
- 現在は複数処理の調整も永続化もないため、アプリケーションサービス（`application_service`）とリポジトリ（`repository`）は置かない。

機能が増えたら、業務領域ごとに上表の責務を分けます。フォルダー名を揃えるためだけの一括移動や、不要な全レイヤーの追加は行いません。

## 継承より明示的な定義と合成

Python・TypeScript・Vueで共通の方針です。継承は基本的に避け、必要なフィールド・依存・処理をその場所で読める形にします。「同じフィールドがある」「同じコードを減らせる」だけでは継承の理由にしません。

- Pythonの入出力モデルは原則 `BaseModel` を直接継承し、別の入出力モデルからフィールドを引き継がない。
- TypeScriptのAPI入出力もフィールドを明示し、別の応答型の `extends`・`Omit`・交差型による機械的な共有を避ける。
- 独立した意味を持つ共通子オブジェクトは型やモデルとして共有してよい。依存する処理は必要に応じて注入し、合成する。
- ページネーションなどの明確な共通仕様に基づく継承・ジェネリック型は例外としてよい。
- `BaseModel`・例外・設定・HTTP応答など、フレームワーク上必要な継承や動作拡張は禁止しない。コード削減だけの独自基底クラスと区別する。

例えば、作成用と応答用のフィールドが似ていても、同じ契約とは限りません。

```python
from pydantic import BaseModel


class PilotCreate(BaseModel):
    name: str


class PilotResponse(BaseModel):
    id: str
    name: str
```

この程度のフィールド定義の重複は許容します。作成用の制約変更が応答へ意図せず波及しないことを優先します。既存の継承を解消する場合も、必須・既定値・制約・validator・余分な項目の扱いなどの契約を維持してください。

## 重複削減だけを目的に関数化しない

見た目が似た数行をまとめることより、責務と変更理由が同じかを優先します。行数や出現回数だけを共通化の基準にはしません。

### 抽出する理由になるもの

- 同じ業務ルールを複数箇所で必ず同時に変更する必要がある。
- 入出力と責務を具体的に命名でき、呼び出し元の意図が明確になる。
- 通信のエラー処理など、同じ契約・境界の処理を一箇所で管理する必要がある。
- 長い処理を、独立した意味と検証可能な境界を持つ処理へ分けられる。

### 避けるもの

- 似ているが別々に変更される処理を、汎用ヘルパーへまとめる。
- 呼び出し元ごとの違いを真偽値・モード・多数の任意引数で切り替える。
- 意味を説明しない `process_data` などの関数を増やし、読むための移動だけを増やす。
- 将来の再利用だけを予想した共通化や、単に別の関数へ引数を渡す中継処理。
- Vueの同じクラス列を減らすためだけのコンポーネント化。UIの責務・操作・状態を共有するかで判断する。

例えば注文一覧と請求書の表示は、文字列整形が似ていても契約や変更理由が異なるなら局所的な重複を残します。一方、同一の料金計算ルールは一箇所へまとめ、表示処理とは分けます。
関数化そのものは禁止しません。一度しか使わなくても、名前で業務上の判断や処理の境界が明確になるなら抽出して構いません。テストも行数削減のために汎用化せず、準備の共有と検証する振る舞いを区別してください。

## エラー処理

### 契約と責務

APIは `code`（安定した公開理由コード）、`reason`（安全な日本語）、必要時の `errors`（fieldとcode）を返します。検証エラーの入力値・内部例外・スタック・接続情報を含めません。
プレゼンテーション（`presentation`）がHTTP応答へ変換し、業務ロジックへHTTPを持ち込みません。未知の例外は安全な500へ変換し、運用ログにも機密情報を含めません。
APIクライアントはHTTP状態と理由コードをApiErrorとして保持し、Composableは共通の表示理由へ変換します。画面は「挨拶を取得できませんでした」のような操作説明を付けます。生のError.message・任意のAPI本文を画面へ出しません。
この最小例は既知コード辞書で表示します。サーバーのreasonはAPI利用者向けの安全な説明であり、本文を無条件に信頼して表示しません。既知コードの5xxも理由を保持し、未知コード・不正JSON・ネットワーク障害には共通文言を使います。

### 状態と再試行

読み込み・成功・失敗を複製せず、Queryの状態から導出します。キャンセルは通常の失敗通知と区別します。更新処理では「失敗が確定」「結果不明」「成功後の再照会失敗」を分け、結果不明時に無条件で再送を促しません。冪等性キー・状態照会などを設計してから再試行します。
現在の例は読み取りだけなので更新処理や結果不明状態は未実装です。多言語化は理由コードを維持してAPIと表示辞書を分けて拡張し、コードに表示文言を埋め込みません。
APIの契約・入力値の非公開、クライアントの未知コードと通信障害、Storyのエラー表示を検証します。[テスト方針](テスト方針.md)を参照してください。
