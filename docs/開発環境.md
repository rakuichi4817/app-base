## miseを入口にする

ルート `mise.toml` でPython・uv・Node.js・pnpmを固定します。プロジェクト側の `mise.toml` は操作だけを定義し、ルートはそれらを集約します。
ローカルとCIで別々のコマンドを管理せず、共通の `mise run check` を使います。

`monorepo_root = true` と `config_roots` で子プロジェクトを列挙しています。プロジェクトを追加した場合は、一覧とルートの集約タスクの両方を更新してください。
miseは子設定の信頼も必要です。自分で管理するコピーの内容を確認してから `mise trust --all` を実行します。

## モノレポと依存管理

モノレポはコードの配置・タスクの集約です。パッケージマネージャーの単一ワークスペースとは分けて考えます。

- coreとbackend：それぞれ `pyproject.toml`・`uv.lock`・`.venv` を持つ。
- backendはcoreをローカルのeditable依存として取り込む。
- frontend：独立した `package.json`・`pnpm-lock.yaml` を持つ。
- frontend内の `pnpm-workspace.yaml` は単一パッケージとビルドスクリプト許可を定義する。ルート全体をpnpmワークスペースにはしない。

独立した依存解決により、プロジェクトの切り出しやツール更新の参考にしやすくしています。共通設定の多少の重複は、各プロジェクトだけでも意味が読めることを優先しています。

## VS Code

1. `mise run install` で各Python環境とフロントエンド依存を用意する。
2. `app-base.code-workspace` を開く。
3. 推奨拡張を導入する。
4. coreとbackendのインタープリターがそれぞれの `.venv/bin/python` か確認する。

ワークスペース共通設定は保存時整形・ty/Ruffの環境参照・ESLintの作業ディレクトリ自動判定を定義します。
各Pythonフォルダーの `.vscode/settings.json` はインタープリター・Ruffの修正・pytestを定義します。ルートフォルダーにもPythonを追加する場合は、その環境を別途設定してください。

Pythonの型チェックと補完はty、Lintと整形はRuffです。Pylanceは推奨から外し、Python拡張の言語サーバーは無効にします。`ty.disableLanguageServices = false` によりtyの言語サービスを有効にしています。
EditorConfigの設定・拡張は使用せず、Pythonは `pyproject.toml`、フロントエンドはPrettier・ESLintの専用設定で管理します。mise拡張（`hverlin.mise-vscode`）は推奨に含めています。
`fromEnvironment` は各 `.venv` のツールを参照する設定です。VS Code側でもCIと同じ版を使うため、最初に依存を導入してください。

インタープリターを過去に手動選択している場合、`defaultInterpreterPath` よりその選択が優先されることがあります。「Python: Select Interpreter」で選び直してください。

WSLではフォルダーをWSL接続で開き、拡張もWSL側に導入します。WindowsネイティブではPythonのパスを `.venv/Scripts/python.exe` に変更する必要があります。
Prettierはfrontendの設定があるファイルだけに適用します。ルートのMarkdownやYAMLには現時点でPrettierの一括検証を設定していません。

## CI・依存更新

`.github/workflows/ci.yml` はmainへのpush・PR・手動実行でUbuntu上の1ジョブを起動します。

1. checkout（認証情報を作業ツリーへ保持しない）
2. mise-actionでツールを導入
3. `mise run install` でロックどおりに依存導入
4. `mise run check` でLint・整形確認・型チェック・テスト・フロントエンドビルド
5. `mise run license`、Storybookビルド、Chromiumの準備、Storyの操作・アクセシビリティ検査

`check` はLint → テスト → ビルドの順です。同じTypeScript増分情報の同時更新を避け、各段階の独立したプロジェクトは並列実行します。権限は `contents: read`、タイムアウトは15分、同一ブランチの古い実行は中断します。
シークレット・クラウド認証・DB・Dockerは不要で、`pull_request_target` は使いません。実APIとのE2EとDockerビルドは別検証です。依存キャッシュ・差分判定・デプロイ・成果物配布は必要時に追加し、このCIではビルド出力を保存・公開しません。
ActionsはコミットSHA固定とし、対応メジャー版をコメントしてDependabotで更新します。ブランチ名がmain以外ならトリガーを変更し、必須チェックはGitHubのブランチ保護で設定してください。GitHub上の動作確認は登録後に行います。

Dependabotは週次でGitHub Actions・2つのuvプロジェクト・frontendのnpm依存を確認し、Python・frontendはグループ化します。coreとbackendのロックの整合性もレビューしてください。miseのツール版は自動更新の対象外で、自動承認・自動マージは設定していません。

## 文書管理・ADR

READMEは概要・前提・起動方法、docsは方針・理由・手順の正本、AGENTS.mdは短い実行指示です。規則変更は関連実装と同じPRで文書とAI指示を更新し、機能仕様だけの変更でAI指示を増やしません。
共通規則はルート、固有規則は対象のAGENTS.mdに置き、親の規則を再掲しません。人間向けの説明はAGENTS.mdを読まなくても理解できるようにします。
重要な設計判断は `docs/ADR/` に背景・選択肢・決定・影響を残します。[ADRテンプレート](ADR/テンプレート.md)を使用し、全変更をADRにはしません。日々の検証結果はPRへ記載し、採用案は現行ガイドへ統合して、検討中と実装済みを混ぜません。

## PR・レビュー

[PRテンプレート](../.github/pull_request_template.md)は概要・種類・関連資料・任意の変更詳細・スクリーンショット／録画を含みます。固定の組織リンクではなく、Issue・タスク・設計資料・Figmaなど必要な参照先を記載してください。
検証欄にはmiseタスクと結果、未実施なら理由を記載します。依存・文書更新が不要な確認項目は、対象外と明記するか削除して構いません。
レビューコメントは `🚨 [must]`（必須修正）、`💡 [want]`（改善提案）、`🔍 [nits]`（軽微）、`💬 [comment]`（質問・補足）で分類します。
